# Step 5 — Best practices

These are the habits that separate "fun demo" from "useful tool in a real
repository". They're written for someone in their first few years, but they're
the same rules senior engineers converge on.

The theme: **the agent is fast and confident, and neither of those is evidence
of correctness.** Your process has to supply the scepticism.

---

## 1. Set the blast radius before you start

An agent runs with *your* permissions. There's no sandbox by default.

- First sessions: a disposable `~/scratch` directory.
- Real work: a branch, not `main`.
- Risky exploration: a separate clone, or a container.

```sh
cd ~/code/my-project
git switch -c try/agent-refactor
```

**Why:** undoing a wrong turn is trivial when the turn was isolated and
miserable when it wasn't. This is the cheapest habit here and the one people
skip.

## 2. Commit before you prompt

```sh
git status          # clean?
git log -1 --oneline
```

If there are uncommitted changes, commit or stash them first.

**Why:** the agent will edit files, and you need to be able to answer "what
exactly changed?" with `git diff`. Without a commit, its changes and yours are
mixed together and code review becomes archaeology.

## 3. Read the diff. Every time.

```sh
git diff
```

Not the agent's summary of the diff — the diff. Summaries are generated by the
same system that made the mistake.

Once you accept a change, it's yours. That's true socially (your name is on the
commit) and technically (you'll be the one paged).

## 4. Deny what can't be undone

This is the highest-value five minutes of configuration in this guide. Create
`opencode.jsonc` in your project root:

```jsonc
{
  "$schema": "https://opencode.ai/config.json",
  "permissions": [
    // Ask before any shell command...
    { "action": "shell", "resource": "*", "effect": "ask" },

    // ...but let routine read-only inspection through without friction.
    { "action": "shell", "resource": "git status *", "effect": "allow" },
    { "action": "shell", "resource": "git diff *", "effect": "allow" },
    { "action": "shell", "resource": "git log *", "effect": "allow" },
    { "action": "shell", "resource": "ls *", "effect": "allow" },

    // Things that leave your machine or destroy data: never.
    { "action": "shell", "resource": "git push *", "effect": "deny" },
    { "action": "shell", "resource": "rm -rf *", "effect": "deny" }
  ]
}
```

Rules are evaluated in order and **the last match wins**, so the specific
allowances sit after the broad `ask`.

A shell pattern ending in ` *` also matches the bare command, so
`"git status *"` covers both `git status` and `git status --short`.

**Why deny push specifically:** a push is the one action that can leak code
publicly or publish a broken release, and it can't be undone by `git reset`. Let
pushing be a thing *you* do after reading the diff.

> `shell` runs with your full user authority and its directory inference is best
> effort. A narrow allowlist beats clever patterns meant to catch every dangerous
> command — you will miss one.

## 5. Plan before build, on anything bigger than a small edit

Switch to the `plan` agent (`Ctrl+X` then `A`), then describe the task:

```text
Plan how to add rate limiting to the public API routes.
Don't write code yet — I want to see which files you'd touch and why.
```

The `plan` agent cannot edit your files. That's a permission, not a promise, so
you can trust it while you think.

Then review the plan as a design document. Does it touch the right files? Did it
miss the auth middleware? Is it about to add a dependency you don't want?

**Why:** the cost of a wrong plan is one message. The cost of a wrong
implementation is a diff review, a revert, and your afternoon.

## 6. Give context by file, not by essay

Instead of a paragraph describing your architecture, point at it:

```text
Review @src/auth/session.ts for token-refresh bugs.
Compare against @src/auth/README.md.
```

Type `@` to fuzzy-search files, then keep typing to narrow. You can attach a
range:

```text
Explain @src/auth/session.ts#20-45
```

**Why:** files are exact and cheap. Prose descriptions are lossy and the agent
will confidently fill gaps with assumptions — usually the wrong ones.

## 7. One concern per session

Don't debug a test failure, then ask for a README update, then refactor a
module, all in one thread. Use `/new` (`Ctrl+X` then `N`) between unrelated
tasks.

**Why:** context accumulates. A session carrying three tasks is slower, more
expensive, and more likely to apply the constraint from task one to task three.

## 8. Tell it how you'll judge success

Vague acceptance criteria produce optimistic claims of success.

Instead of:

```text
Add input validation.
```

Say:

```text
Add input validation to the signup handler.
Success means: `npm test -- signup` passes, and posting a 200-character
email returns 400. Show me the test output before you say it's done.
```

**Why:** you're giving it a verifier. The agent can't hear audio and can't
"just know" — it needs a check it can run.

## 9. Write `AGENTS.md` early, and keep it short

This is the highest-leverage file in the repo. It's loaded automatically and
applies to everyone working here.

```md
# Project instructions

- Run `bun typecheck` after changing TypeScript.
- Tests: `bun test <path>`. Never run the full suite locally; CI does that.
- Database queries live in `src/database`. Don't put SQL elsewhere.
- Don't edit files in `src/generated/` — they're rebuilt from schema.
- If a change touches auth, stop and ask.
```

Three rules for writing it:

- **Commands first.** Exact commands beat descriptions of commands.
- **Constraints, not aspirations.** "Don't touch generated files" is useful;
  "write clean code" is noise that costs tokens on every request.
- **Short.** It's in context on every turn.

Placement matters: `AGENTS.md` in a directory applies to that subtree, and
OpenCode loads the global file plus every one from your workspace upward.
`~/.config/opencode/AGENTS.md` holds your personal, cross-project preferences.

> OpenCode V2 reads `AGENTS.md` only. A `CLAUDE.md` left over from another tool is
> **not** used as a fallback — port it deliberately if you want it.

## 10. Keep secrets out of the conversation

Defaults already ask before reading `.env` and `.env.*` (and allow
`.env.example`). Two more habits:

- **Never paste a key into a prompt.** Prompts are stored in the session
  database and sent to a provider.
- **Use environment injection** rather than a key in config:
  `opencode service set env ANTHROPIC_API_KEY ...`

If a key does end up in a message or a file, treat it as compromised and rotate
it. Deleting the message isn't enough — it was transmitted.

## 11. Budget attention, not just money

Token cost is visible and manageable. Attention cost is the thing that actually
hurts:

- A 400-line diff you skim is worse than no diff, because now you *believe*
  you reviewed it.
- Three parallel agent sessions produce three streams you can't hold in your
  head.
- "It's working, I'll stop watching" is how an agent gets twenty commits into a
  wrong direction.

Keep tasks small enough to review properly. The bottleneck should be your
review, not the agent's generation.

## 12. Add the rule after the mistake

Don't try to anticipate every failure. When the agent does something you don't
want, add a line to `AGENTS.md` or a `deny` rule — then it can't happen twice.

That's the real loop, over weeks: not better prompting, but a repository that
gets progressively harder to break.

---

## Anti-patterns

| Don't | Do instead |
| --- | --- |
| "Fix the tests" | "Run `bun test src/auth`, then fix the failing assertion" |
| Reviewing the agent's summary | Reviewing `git diff` |
| Letting it push | Pushing yourself, after reading the diff |
| One marathon session for the day | `/new` per task |
| Pasting a stack trace with no file context | `@` the file, then the trace |
| Accepting "done" | Running the verification yourself |
| 500-line diffs | 50-line diffs, reviewed properly |
| Secrets in `opencode.json` | `/connect`, or environment injection |
